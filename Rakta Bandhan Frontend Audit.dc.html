This is a read of the app as it exists today: what each screen is for, where it holds together, and where it does not. Nothing here has been applied to the repository. The backend seam — services/backend.dart, Firebase, Firestore, auth, schemas and rules — is treated as fixed throughout, and every recommendation below is a presentation-layer change that reads the same data the current screens already read.

01

State of the build

The app is further along than a first look suggests, and less coherent. Roughly a third of the screens have already been rebuilt against the design_new/ proposals — warm cream ground, serif display numerals, the droplet motif, one raised object per screen. The rest still run the earlier flat card system. Both live in the same theme file at once, and the theme file says so out loud.

Layer A — redesigned
11
Splash, Login, Home, Profile, Notifications, Donation history, Create request, Matching, Request detail, and the two ember outcome screens. Warm ground, serif display, droplet vocabulary.
Layer B — legacy flat
10
Requests, Find donors, Donor details, Tracking, Settings, Cooldown, OTP, Registration, Consent, Verifying. Pill tabs, status chips, gradient hero cards, 14px radius everywhere.
Layer C — admin console
5
Admin login, dashboard, donor detail, request detail, hospital form. Reached through a "Admin (temporary)" row in user Settings. No design pass at all.
Layer D — designed, never applied
6
Personal information, Emergency contact, Terms, Privacy policy, Data usage, Consent preferences. Written in design_new/flutter/, absent from lib/screens/. Their entry points currently fire a toast.
The core finding: the app runs two design systems side by side

lib/theme/app_colors.dart declares both. One set — pageBackground, border, statusUrgentBg, statusPendingBg, tabTrackBackground — drives the flat screens. A second set — warmPageBackground, cardBorderWarm, dividerWarm, warmAmberBg, warmGreenBg, textPrimaryWarm — drives the redesigned ones. The file's own comment says the two are "deliberately separate" and "distinct near-duplicate shades… don't collapse them into one." That was a sound call while the redesign was partial. It is now the single biggest source of visual drift: #F7F6F2 against #FBF7F1, #1A1A1A against #241416, #E5E3DD against #EEE8DF — differences too small to read as intent and too large to read as the same product.

02

Flows, as built

Flow 1 — entry
Launch to verified donor
Splash › Onboarding ×4 › Login (phone) › OTP › Registration › Consent › Verifying › Home
Splash routes on two facts: has a donor profile, has seen onboarding. Seven screens before the product is visible.
Flow 2 — donor
Alert to donation
Home / Notifications › Request detail › Accept result › Match contact › Donation confirm › Cooldown
The emotional spine of the product. Accept enforces one active match at a time by query, and can land on blocked or already-claimed.
Flow 3 — requester
Need to match
Create request › Matching ladder › Donor found / No donor found › Tracking › Requests tab
The request document is real; the ladder animation is a front-end simulation whose outcome is decided from a real snapshot of compatible donors.
Flow 4 — discovery & identity
Map, profile, history
Find donors (map + sheet) › Donor details · Profile › Donation history › Settings › Admin console
Only three of these are in the tab bar. Find donors is reached from a small grey text link at the bottom of Home.
Navigation problems that are really visual problems
  • Three tabs — Home, Requests, Profile — carry a product with four flows. The map and the requester flow have no permanent home, so both are demoted to text links at the bottom of a scroll.
  • The Requests tab is pushed as a tab but built as a pushed screen: it renders its own back arrow in an AppBar, which does nothing meaningful from a tab root.
  • Every deep screen constructs its own header. Three different patterns coexist: a real AppBar with a centred 18/w500 title, a hand-built 52px Stack with a 17/w600 title, and a hand-built 48px Row with a left-aligned 16/w600 title.
  • Outcome screens are pushed rather than replaced in several places, so the back stack can return the user to a request they have already accepted.
  • Nothing in the shell ever shows the donor's own live state — availability, cooldown, or an unread alert count — except on the two screens that happen to render it inline.
03

Screen-by-screen audit

Each card: what the screen is for, what it puts first, what is wrong, what is thin, and where it should go.

Splash & Onboarding Layer A 4 intro pages splash_screen.dart · onboarding_screen.dart
Purpose
A brand reveal, then a four-page argument for registering — and the one gate that decides where a returning user lands.
Hierarchy today
Logo plate at 176px on cream, tagline fading in beneath. Onboarding page 1 uses the ember gradient field; pages 2–4 return to the light ground.
Problems
The mark is a 4160×4160 JPEG on a white rounded plate — a logo in a box, not a logo. A transparent PNG exists in design_new/ and is unused. The reveal holds 550ms after decode, then a 400ms fade, on every cold launch forever.
Direction
Drop the plate; set the transparent mark directly on the ground and let the ember field arrive behind it, carrying straight into onboarding page 1 as one continuous move. Shorten the hold for returning users.
Login · OTP · Registration · Consent · Verifying Mixed layers login · otp · registration · consent · verifying
Purpose
Phone-number identity, then the donor record: name, blood group, location, eligibility — and the consent the product needs before it can page anyone.
Hierarchy today
Login is the strongest screen in the app: brand mark, serif welcome, one pill-shaped country + phone field, one filled button. The screens after it revert to stacked 14px-radius form fields under a plain AppBar.
Problems
Login's radius is 30px; every other field in the app is 14px. The hands_heart.png illustration is dropped in at the foot of Login at full width with no size or crop control, and appears nowhere else. On web the whole flow stretches to the browser width — the phone field becomes a 1700px bar. Registration asks for everything on one long scroll with no sense of progress.
Direction
Make Login's treatment the standard for the whole entry sequence: one question per screen, generous type, a persistent thin progress rule, and the ember field reserved for the consent moment. Bring the illustration under a fixed art frame or retire it.
Home Layer A Tab 1 home_screen.dart
Purpose
One live nearby request, the donor's own state, their record, and a quiet way to become a requester.
Hierarchy today
Greeting and first name in 30px serif, availability pulse, then the single request card as the only raised object, then the donation count at 44px serif with five droplets. Deliberate and mostly working.
Problems
It shows docs.first — the newest open request, not the nearest or the most compatible — and hard-codes "just now" as its timestamp regardless of age. Blood-group compatibility is not filtered here, so a donor can be shown a request they cannot fulfil; the Requests tab does filter. Distance renders "—" until GPS resolves. The empty state is a single grey sentence where the product's whole argument should be. "SOMEONE NEEDS YOU" sits in 11px letterspaced caps above a card that already says it.
Direction
Keep the one-object composition, fix what it selects: nearest compatible request, real elapsed time, live distance. Give the caught-up state real substance — the donor's own standing, days to eligibility, what happened nearby this week. This is the screen most users see most often and it currently ends in a grey line of text.
Requests Layer B Tab 2 requests_screen.dart
Purpose
Two inboxes in one screen: open requests this donor can fulfil plus what they have accepted, and the requests they themselves raised.
Hierarchy today
A solid-red pill tab track, then identical white cards. Every card carries a status badge, a droplet, a location line and one or two buttons of equal weight.
Problems
The clearest example of the two-system split: this screen mixes flat status colours with warm redesign tokens in the same card. Nothing is ranked — a critical request four hours old looks exactly like a normal one raised yesterday; urgency is not shown at all in the card. "Track status" and "Cancel request" are both outlined buttons of the same size, so cancelling is as easy as checking. The location line silently falls back to "1 unit(s) needed" as a title. It back-arrows out of a tab.
Direction
Rebuild as one ranked list with real segmentation — urgency and distance drive order and visual weight; matched requests carry the donor's face and a live status line; terminal states drop to a quiet archival row. One primary action per card, destructive actions demoted to text.
Find donors — map Layer B Highest-risk screen find_donors_screen.dart · donor_details_screen.dart
Purpose
Browse available donors near a searched location, filter by group, open a donor, or fire a request.
Hierarchy today
A search field and nine filter chips float over the map; a fixed 340px white sheet holds the ranked donor list. Markers are avatar discs with a group droplet and a pointer tail — the best-drawn objects in the app.
Problems
There is no map. The ground is a flat #E8E6E1 fill with three hand-painted grey strokes, and the two donor markers are pinned at hard-coded pixel coordinates that bear no relation to their real latitude and longitude — the sheet's distances are real, the picture is not. A "you are here" halo is drawn at fixed 200/165 as well. The sheet cannot be dragged despite having a drag handle. Only two of N donors ever get a marker. Both card buttons are outlined, so "Request" — which writes a live urgent request document — reads as secondary. The nine chips overflow horizontally with no affordance.
Direction
Two honest options, and this needs your decision: either a real tiled map with correctly projected markers and a draggable sheet, or drop the map entirely and design this as a proximity list — concentric distance bands, the donor's disc placed by bearing and range rather than by street. The current halfway state reads as a broken map, which costs trust on the screen where trust matters most. Keep the avatar-disc marker either way.
Create request Layer A create_request_screen.dart
Purpose
Three questions — group and units, urgency, location — asked one at a time, all answers staying visible and editable.
Hierarchy today
"Who needs blood?" in 27px serif, then question blocks separated by hairlines. The live question carries a red ring marker; answered ones collapse to a green check row. Structurally the most sophisticated screen in the app.
Problems
The selection states are unfinished: all eight blood-group droplets render identically in neutral grey with no selected state — selection is only visible after the section collapses. Urgency radios never fill, and the bars weight defined for each level is never drawn. Units are steppable in two different places with different type sizes. The three "ring markers" are hand-built circles here, while widgets/ring_field.dart and step_tracker.dart already exist. Location errors introduce a left red rule that appears nowhere else in the app.
Direction
Keep the flow exactly as approved; finish its states. Selected droplet fills crimson, urgency draws its three-bar weight and a filled radio, one units control, and the question marker becomes a shared component with the tracker used on Matching and Tracking.
Matching ladder & outcome screens Layer A · ember field matching · donor_found · no_donor_found · accept_result · match_contact · donation_confirm · cancel_confirm
Purpose
Hold the requester through the wait, then deliver the result: a donor, or none. Then the seven small screens that close every branch of both flows.
Hierarchy today
Matching is the app's one dark screen: a near-black red gradient, concentric rings, a rotating sweep, anonymous notified-donor dots, the group droplet at centre, and a stage ladder in a glass panel. The outcome screens share an ember field and a light inverted button.
Problems
Matching uses gradientMatchingStart/End while the outcome screens it flows into use gradientEmberStart/Mid/End — two different dark fields back to back. Seven near-identical outcome screens each rebuild their own layout, so paddings, button styles and copy tone drift. The dark screens sit outside the theme entirely: white-with-alpha values are written inline, and the ladder's success green #7FCB8E exists nowhere else. The sweep animation runs on a 3400ms loop with no relation to the ladder's real stage timing. Several outcomes are pushed rather than replaced.
Direction
One ember field, one dark-surface token set, and one outcome template — full-bleed field, one line of serif truth, one supporting line, one primary action, one quiet escape — that all seven screens fill in. Tie the sweep to real stage transitions so the motion means something. This is where the product earns the word "meaningful"; it should feel like the same room throughout.
Tracking Layer B tracking_screen.dart · widgets/step_tracker.dart
Purpose
Live status of one request across four steps, read straight from the request document.
Hierarchy today
A red gradient hero card with the group and location, then a white card holding the four-step tracker.
Problems
The GradientHeroCard here is the last survivor of a treatment the redesign explicitly removed from Home — a red gradient block competing with the content below it. Cancelled and expired both render as a grey "pending" step, so a cancelled request looks like it is still waiting. The matched step names the donor but offers no way to reach them, though Match contact exists. Terminal states show an alert triangle in a grey square that appears in this shape nowhere else.
Direction
Retire the gradient hero. Lead with the request in plain warm type, make the tracker the object on the page, give failed steps their own crossed state, and put the matched donor's disc and a contact action inside the matched step.
Profile · Donation history · Cooldown Layer A Tab 3 profile · donation_history · cooldown
Purpose
Donor identity and standing: who you are, whether you are available, what you have given, when you are eligible again.
Hierarchy today
Initials avatar with the group droplet attached, name in 26px serif, verification pill, an availability card with a switch, the count at 48px serif, then a four-row menu. History repeats the same count at 44px over a ten-droplet trail and a real vertical timeline.
Problems
The impact trail is drawn three times at three horizons — five droplets on Home, four on Profile, ten in History — so the same donor's progress reads differently on each screen. Profile's "Personal information" and "Emergency contact" rows open a toast, not a screen; both screens exist in design_new/flutter/ and were never applied. Cooldown is reachable only if you already know it exists, and its 18-segment bar, Profile's 11-segment bar and History's 10-droplet trail are three renderings of one idea. Cooldown still uses statusPendingText amber from the flat system. Verification pending is stated but never explained — no idea what happens next or how long.
Direction
One impact-trail component with one fixed horizon, used everywhere. Fold Cooldown into Profile as the eligibility state of the availability object rather than a screen you cannot find. Ship the two missing screens. Give verification a real explanation and a visible stage.
Notifications Layer A notifications_screen.dart
Purpose
The alert feed — one actionable item promoted, everything else archival.
Hierarchy today
Exactly one raised card with a red top edge and the only button; earlier items as hairline-divided rows with a dot or a green droplet. The rule is well chosen and well executed.
Problems
Its one button opens a toast — "Opening request — coming soon" — so the app's most urgent surface is a dead end, though RequestDetailScreen already takes a request id. "Enable notifications" is also a toast. Home's bell shows a static red dot that is never tied to unread state. Timestamps arrive pre-formatted as strings from the service, so nothing can group by day. Three hard-coded browns appear here and nowhere else.
Direction
Wire the card to the request it names, bind the bell to real unread count, group the archive by day, and pull the amber and brown values into tokens. No new design needed here — this screen mainly needs to be connected.
Settings & Admin console Layer B / C settings · admin_login · admin_dashboard · admin_donor_detail · admin_request_detail · admin_hospital_form
Purpose
Privacy and account controls for the donor; verification, request moderation and hospital records for staff.
Hierarchy today
Three bordered groups of plain rows. Every actionable row is crimson text of identical weight, so "Download my data", "Request data deletion" and "Log out of all devices" all look the same. Admin is a separate visual world reached from the bottom of this list.
Problems
Settings is the weakest screen in the app. Section headings are 12px uppercase muted grey — the only place that pattern appears. The "Show exact address to matched donors" toggle is local state that is never persisted, on a genuinely sensitive privacy promise. Two of the three account actions are toasts. Data deletion, an irreversible action, has no confirmation and no destructive styling. There is no legal section at all, though five legal screens exist in design_new/flutter/. "Admin (temporary)" ships a staff back door inside the consumer app.
Direction
Rebuild Settings on the standard grouped-row component with real section headers, one destructive treatment, persisted privacy state, and the legal documents in place. Move the admin entry behind something that is not a row in the user's own settings, and give the console its own coherent frame — it is a different product for a different person and should look like one.
04

Cross-cutting problems

01 — Colour
Two palettes, one app
Flat and warm token sets coexist by design decision. Nineteen colour values also appear inline across screens — #7FCB8E, #7A4A08, #8A7350, #E0A8AF, #FFF9F5, every Colors.white.withValues on the dark screens — outside the theme entirely.
02 — Type
A five-step scale spent across twenty sizes
The theme defines five text styles. Screens use 10.5, 11, 11.5, 12, 12.5, 13, 13.5, 14, 14.5, 15, 15.5, 16, 17, 18, 19, 20, 24, 26, 27, 30, 32, 44 and 48px — nearly all written inline. Titles alone come in 16/w600, 17/w600, 18/w500 and 19/w500. The serif display face is used well, but by direct call rather than by scale step.
03 — Shape
Twelve radii where the spec says one
The style guide mandates 14px throughout. In practice: 8, 9, 10, 14, 15, 16, 18, 20, 22, 24, 30 and 32px. Screen padding varies too — 20, 24 and 28px left/right on screens that sit next to each other in the same flow.
04 — Components
Thirteen widgets, mostly bypassed
widgets/ holds a droplet, ring field, step tracker, status badge, state card, avatar badge, pulsing dot, distance connector, filter chips, loading button, two-person connection and brand mark. Screens then hand-build avatars, ring markers, section labels, headers, timeline rails, stat blocks and progress bars anyway. Same idea, five implementations, five sets of values.
05 — Dead ends
Eight toasts standing in for screens
Personal information, Emergency contact, notification permissions, opening a request from a notification, data export, data deletion, and the two contact actions on the match screens all resolve to a SnackBar. Six of these have real designs sitting unapplied in design_new/flutter/. A polished product cannot have its most urgent button open a toast.
06 — Emptiness
The states most users see first are the thinnest
A new donor in a city with no open requests sees: a grey sentence on Home, an empty Requests tab, a zero on Profile, an empty timeline in History, and no donors on the map. Five screens, five grey lines. Loading is a bare CircularProgressIndicator in fourteen places; nothing is skeletonised.
07 — Imagery
Two assets, one used badly
The whole app ships one 4160px logo JPEG and one illustration, placed once, unconstrained. There is no image language — no portraiture, no texture, no illustrative system. "Visually rich" cannot be reached on type and geometry alone, and this is the largest gap between the current build and the stated target.
08 — Motion
Four animations, no shared timing
The splash reveal, the matching sweep, the pulsing dot and the ring field each define their own durations and curves. Screen transitions are default Material pushes except one hand-rolled fade. Nothing animates on state change — accepting a request, toggling availability, a match arriving.
05

Proposed design system

Not a new look. The redesigned screens already contain the right instincts — warm cream ground, crimson as the only saturated colour, serif for the human numbers, the droplet as the unit of everything, one raised object per screen. The proposal is to promote that into the single system for the whole app, resolve the duplicate tokens in favour of the warm set, and add the two things it does not yet have: an image language and a defined motion vocabulary.

Foundation 01
Ground, ink, crimson

The warm set wins; the flat set is retired. Cream ground, warm near-black ink, and one crimson doing every job that needs saturation. Status meaning comes from two muted supports only — a forest green and an ochre amber — never a third hue.

Foundation 03
Space, shape, elevation

4px base. Screen gutter fixed at 24px, everywhere, including the screens currently at 20 and 28. Three radii instead of twelve: 12 for controls and inputs, 20 for raised objects, full round for discs and droplets only.

Elevation carries meaning rather than decoration. Ground level is the page: dividers, hairlines, no fills. Raised is reserved — one object per screen, white on cream with a soft warm shadow. The ember field is its own plane and never mixes with either.

Foundation 04
The device vocabulary

Six recurring objects carry the product's character. All six already exist in some form; the proposal is that each has exactly one implementation, one set of sizes, and one meaning.

  • Droplet — the unit of blood group, of a donation given, of a request. Four sizes, filled or empty, never re-drawn.
  • Identity disc — initials or portrait, with the group droplet attached at the corner. The same object in a card, on the map, in a tracker step and in a header.
  • Live pulse — availability and searching. The only animated dot in the app.
  • Connector — the line between two people, with distance or status on it. Used on cards, matches, and the tracker.
  • Ring field — concentric range rings. Matching, the map's proximity bands, the create-request marker.
  • Impact trail — droplets given against one fixed horizon. One horizon, all three screens.
Foundation 05 — the missing piece
An image language

This is what separates the current build from "premium, warm, human". Type and geometry alone read as austere; the target needs texture and faces. Three proposed registers, each with a fixed frame so nothing is ever dropped in unconstrained again:

  • Portraiture — real donors and recipients, warm-toned, in identity discs and in the outcome screens. The single highest-impact addition.
  • Full-bleed field art — one image per emotional peak, behind the ember gradient at low opacity: onboarding, match found, donation confirmed.
  • Line illustration — a small consistent set for empty states and eligibility explanation, in crimson on cream, replacing the five grey sentences.

This needs you. I cannot generate photography, and any illustration I draw will be a rough sketch rather than finished art. If you can supply real photography — or approve commissioning it — the redesign gets substantially warmer. If not, I would rather propose a texture-and-type direction that looks deliberate than fill the gap with weak drawings.

Foundation 06
Motion, with a job

Three durations — 160ms for controls, 320ms for transitions, 700ms+ for the two brand moments — on one easing curve. Motion is spent on four things only:

  • A request arriving: the card rises into place rather than appearing.
  • Accepting: the droplet fills, the connector draws, the screen becomes the field.
  • The search: the sweep tied to the ladder's real stage changes, not a free-running loop.
  • Standing changing: a donation added to the trail, availability toggling, eligibility reached.

Everything else — page pushes, list scroll, sheet drag — takes the platform default. Fewer animations, each meaning something.

06

The rules that make it one product

One raised objectEvery screen has a single thing at raised elevation — the live request, the tracker, the availability state. Everything else sits on the ground. This rule already governs Home and Notifications; extending it is most of what makes the app feel considered.
One primary actionOne filled crimson button per screen. Secondary actions are outlined, destructive ones are plain text and always confirmed. Fixes Requests, Find donors and Settings at a stroke.
One header componentEvery pushed screen uses the same header: back affordance, title at one size, optional single action. Replaces three coexisting patterns.
The field is for peaks onlyFour moments earn the ember field: the brand reveal, consent, the search, and the match. Using it anywhere else spends it.
Empty is a designed stateNo screen ends in a grey sentence. Every empty state gets an illustration or a device, a line of real copy, and one thing to do.
Serif means humanNames, counts, dates and headlines in serif. Labels, buttons, fields, navigation and status in sans. No exceptions in either direction.
The one structural change I would recommend

Three tabs cannot hold four flows, which is why the map and the requester journey are currently text links at the bottom of a scroll. Proposal: four tabs — Home, Requests, Nearby, You — with the requester entry raised to a persistent action rather than a link, and the donor's live state (available / cooldown / unread) visible in the shell on every screen.

This changes navigation, not data: every destination already exists and every screen already reads its own stream. It is the single change that would do most for the "one coherent product" goal, and it is also the one I least want to make without your approval.
