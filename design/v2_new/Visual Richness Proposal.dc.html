Visual richness — proposal
Six devices, not twelve illustrations
The approved system stays exactly as it is. What's added is a second layer of recurring visual devices that carry product meaning — so richness comes from the same vocabulary appearing everywhere, not from each screen inventing its own artwork.
The six devices
Group token
Blood group inside a droplet. A group is never a rectangle again.
Person
Initial disc + live ring. Human presence, honestly — no stock faces.
Radius
The ring system carrying real distance. Spatial, not decorative.
Connection
Hairline joining two people. Solid when live, dashed when pending.
Compatibility
Which groups can answer this need, shown as relationship.
Impact trail
Donations as a sequence of drops. Cumulative, not a number.
Opacity never wraps text
Recession — distance, archival status, expiry — is carried by the devices only: droplet fill and size, avatar disc tint and diameter, dot colour, rule weight. A container opacity that encloses a string silently invalidates that string's measured contrast, so it is never used for that purpose here.
Text steps down by weight and token instead: #241416 primary (14.1:1), #3D3630 archival titles at w500 (10.5:1), #6E6A62 muted (5.04:1) — all measured on #FBF7F1, all clearing AA at every size used. On the map's lightest disc (#F6F2EA) #6E6A62 measures 4.70:1.
Rhythm is deliberate
Onboarding RICH → Home RICH → Requests LIVE → Create GUIDED → Matching ALIVE → Match EMOTIONAL → Profile IDENTITY → Settings/Legal QUIET. Settings and the legal screens are deliberately left as they are — a product where every screen is decorated has no peaks.

What is unchanged
Every token, surface rule, elevation rule, CTA level, motion duration and spacing value from the approved system. No gradients added outside the two existing red fields. No new colours. No screen gained a second card. Settings, the legal set, admin login and OTP are deliberately untouched — the rhythm needs quiet screens to make these read as rich.
On photography: the brief mentions human imagery. The product has no photo upload and no avatar field in the donor schema, so every person here is an initial disc. That is an honest constraint, not a placeholder — if you want real faces, it needs a backend field and a moderation policy first, which I'd raise as a separate product decision rather than mock in.
